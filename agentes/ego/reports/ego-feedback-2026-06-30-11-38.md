# Ego Feedback — Hallazgo crítico de seguridad (2026-06-30, 11:38)

## Estado
🔴 **ROJO** — vulnerabilidad de exposición de credenciales abierta y confirmada en producción

## Hallazgo crítico
El script de protección de la columna `accounts.password` (`revoke select (password) on accounts from anon, authenticated;`) se ejecutó sin error ("Éxito. No se devolvió ninguna fila."), pero **verificación en vivo contra la API REST pública confirma que la columna sigue siendo legible**:

```
curl .../rest/v1/accounts?select=password → HTTP 200, []
```

Una respuesta `200` (en vez de un error de permisos de Postgres) significa que el `REVOKE` no tomó efecto real, pese a no haber arrojado error en el SQL Editor. Causa probable: Supabase configura por defecto `ALTER DEFAULT PRIVILEGES ... GRANT ALL ON TABLES TO anon, authenticated` a nivel de tabla; la interacción entre ese grant de tabla y un `REVOKE` a nivel de columna no se comportó como se esperaba.

**Impacto si no se corrige:** una vez existan cuentas reales, cualquier persona con la anon key (pública, visible en el bundle JS del sitio desplegado) podría leer `accounts.password` en texto plano vía la REST API de Supabase, sin pasar por la UI ni por las funciones RPC.

## Plan de remediación en curso
1. Se pidió al usuario correr una consulta de diagnóstico (`information_schema.column_privileges` filtrado por `accounts`) para ver exactamente qué privilegios quedaron activos por rol/columna.
2. Pendiente: con ese resultado, aplicar la corrección exacta (probablemente requiere `revoke select on accounts from anon, authenticated;` a nivel de TABLA completa primero, y luego re-otorgar columna por columna las permitidas, en vez de intentar restringir solo `password` desde un grant de tabla completo).
3. Re-verificar con la misma prueba `curl ?select=password` — debe responder con error de permisos, no `200 []`.

## Bloqueo de uso recomendado
**No se recomienda que el usuario cree su cuenta real ni invite a otros asesores hasta cerrar este hallazgo**, dado que las contraseñas se almacenan en texto plano (sin hash) y actualmente son potencialmente legibles por terceros.

## Nota sobre la falla del hook
El hook automático de Ego no pudo persistir este reporte por restricciones de permisos en modo "don't ask". Generado manualmente con el detalle técnico completo del hallazgo, ya que es información crítica que debe quedar trazada.
